# LESSONS — 사용자 피드백으로 누적된 규칙

`diagram-deck` 을 쓰기 전에 **이 파일을 먼저 읽는다.**
여기 있는 것은 전부 실제로 지적받았거나 실제로 사고가 난 것이다. 예외 없이 지킨다.

새 항목은 `diagram-deck-upgrade` 스킬이 추가한다. 손으로 아무거나 넣지 마라.

---

## A. 파일이 깨지지 않게 (PowerPoint 손상 경고)

### L-01 `a:rPr` 의 자식 순서는 latin → ea → cs
- **지적**: "맥으로 옮겨서 보니까 *PowerPoint에서 …내용에 문제가 있습니다. 프레젠테이션 복구가 시도될 수 있습니다*" 라고 뜬다
- **원인**: 한글 폰트를 넣으려고 `a:ea` / `a:cs` 를 삽입할 때 `latin → cs → ea` 순서가 됐다.
  DrawingML `CT_TextCharacterProperties` 는 자식 순서를 강제한다. LibreOffice·python-pptx 는 통과시키지만
  PowerPoint 는 손상으로 판정한다. 한 파일에서 5,376건 발생했다.
- **규칙**: 글꼴은 반드시 `deck.style(run, ...)` 로만 지정한다. XML 을 직접 만지지 마라.
  꼭 만져야 하면 `latin.addnext(cs)` 다음 `latin.addnext(ea)` 순으로 넣어 latin→ea→cs 를 만든다.
- **검사**: `check_ooxml.py` 가 전 슬라이드의 `a:rPr` 자식 순서를 본다. 위반 0 이어야 한다.

### L-02 좌표는 정수 EMU 여야 한다
- **원인**: `(BODY_W - gap*(n-1))/n` 같은 계산이 실수를 만들어 `x="2670596.6"` 이 XML 에 박혔다.
  EMU 는 `xsd:long` 이라 실수는 스키마 위반이다.
- **규칙**: 도형·그림·표를 놓을 때 좌표는 전부 `deck.E()` 를 통과시킨다.
  `deck.py` 의 `rect/tbox/arrow/hline/table` 은 이미 그렇게 돼 있다. 새 함수를 만들면 똑같이 해라.
- **검사**: `check_ooxml.py` 가 `x/y/cx/cy` 를 전수 조사해 소수가 있으면 실패시킨다.

### L-03 줄바꿈은 `<a:br/>` 다. run 안의 `\n` 은 줄바꿈이 아니다
- **원인**: `run.text = "첫줄\n둘째줄"` 이 `<a:t>` 안에 날 개행을 넣는데, DrawingML 에서 그것은
  줄바꿈이 아니다. PowerPoint 는 한 줄로 이어 그린다 — **열리기는 하는데 내용이 잘못 보인다.**
- **규칙**: 여러 줄 텍스트는 `deck.para()` / `deck.label()` 로 넣는다(내부에서 `add_line_break()` 를 쓴다).
  직접 run 을 만들면 `\n` 으로 나눠 `p.add_line_break()` 를 사이에 넣어라.
- **검사**: `<a:t>` 안에 날 개행이 있는지 grep. 0 이어야 한다.

## B. 그림을 객체로 넣을 때

### L-04 선택 박스가 그림보다 크면 안 된다
- **지적**: "객체 선택 박스가 쓸데없이 크게 그려지지 않게 주의해줘"
- **원인**: SVG 를 viewBox 크기 그대로 PNG 로 만들면 그림 주위 빈 곳까지 이미지에 들어간다.
  PPT 에서 그림 도형 크기 = 선택 박스 크기라서, 빈 여백만큼 선택 박스가 커진다.
- **규칙**:
  1. `svg2png.render()` 로만 렌더한다. 렌더 후 흰 여백을 자동으로 잘라낸다.
  2. **SVG 에 흰 배경 사각형을 깔지 마라.** 깔면 트림할 여백이 없어져 규칙 1이 무력해진다.
  3. 그림을 PPT 에 넣을 때 테두리 사각형을 따로 그리지 마라(`d.diagram()` 은 안 그린다).
- **검사**: 렌더 결과 높이가 viewBox 높이의 97% 를 넘으면 "배경 사각형 의심" 경고를 낸다.

### L-05 그림은 독립 객체로 넣는다. 배경으로 깔지 않는다
- **지적**: "내가 직접 제어할 수 있도록 객체형태로 삽입해주고"
- **규칙**: 슬라이드 배경(`bg`)이나 레이아웃 자리표시자에 넣지 마라. 옮기고 키울 수 있어야 한다.
  **내가 그린 SVG 도해는 여기서 한 발 더 간다 — L-15 를 따라 네이티브 도형으로 넣는다.**
  `d.diagram()`(PNG 한 덩어리)은 논문에서 잘라온 래스터 그림에만 쓴다.
- **검사**: 도형이 실제로 존재하는지, 종횡비 오차가 0 인지 확인한다.

---

### L-15 도해는 그림 파일이 아니라 **네이티브 도형**으로 넣는다
- **지적**: "그림은 통채로 독립개체가 아니라 SVG로 그려진걸 내가 ppt에서 수정할 수 있게 각각 개체로 해달라는거지"
- **원인**: `svg2png.render()` 로 PNG 를 구워 `add_picture()` 했다. 도형 하나이긴 해도 통짜 그림이라
  PowerPoint 에서 글자 한 줄, 상자 색 하나 못 고친다. "객체로 삽입"을 그림 도형으로 오해했다.
- **규칙**: 내가 그린 SVG 도해는 **반드시** `svg2shapes.add_svg_shapes()`(또는 `deck.diagram_svg()`)로 넣는다.
  `rect·circle·line·polygon·text` 가 각각 PowerPoint 도형이 되고 전체는 그룹 하나로 묶인다
  (옮길 땐 그룹째, 고칠 땐 그룹 안으로 들어가 개별 편집).
  PNG 는 **원본이 이미 래스터일 때만** 쓴다 — 논문에서 잘라온 그림·스크린샷.
- **검사**: `check_shapes.py` — pptx 안 도형을 SVG 로 되돌려 원본과 픽셀 비교(**2% 초과면 실패**),
  그룹 경계가 자식 경계와 정확히 같은지 확인. `check_layout.py` 는 **그룹 안까지 재귀**해야 한다
  (안 그러면 도해 슬라이드는 최상위에 그룹 하나뿐이라 사실상 무검사가 된다).
  민감도(실측): 도형 1개 삭제 = 100%, 라벨 하나가 0.44in 밀림 = 2.4%, 상자 색 하나 바뀜 = 46%,
  정상 = 0.1% 안팎. 2% 는 "라벨 하나가 0.4in 밀린 정도"에 해당한다.

### L-16 그림 안 글자가 슬라이드에서 몇 pt 가 되는지 재고 배치를 정한다
- **원인**: 도해를 설명 옆에 반폭(6.5in)으로 놓으니 940 유닛짜리 그림이 줄어 라벨이 **5pt** 가 됐다.
  PNG 일 때는 "작은 그림"으로만 보였지만, 네이티브로 넣으면 그대로 5pt 글자다.
- **규칙**: 도해는 **슬라이드 폭을 다 쓰게** 놓고 설명은 아래 띠나 다음 장으로 뺀다.
  세로 공간이 곧 글자 크기다(대부분의 도해는 가로세로비가 2.5 미만이라 높이에 걸린다).
  조립 후 그림 안 **최소 글자 pt** 를 출력하고, 6.5pt 미만이면 설명을 다음 장으로 옮겨 그림을 키운다.
  - **SVG 를 그릴 때 viewBox 높이를 280~400 으로 잡아라.** 그러면 애초에 이 문제가 안 난다.
    실측: H 515 → 6.1pt, H 510 → 6.3pt, H 356 → 8.6pt.
  - **불릿을 줄이는 것으로는 그림이 안 커진다.** `diagram_svg(items=...)` 는 items 가 **하나라도 있으면
    최소 0.80in** 을 설명 띠로 떼 간다(`need = max(Inches(0.80), …)`). 4줄을 2줄로 줄여도 그림 높이는 그대로다.
    6.5pt 를 못 맞추면 **`items` 를 통째로 `None` 으로 비우고 그 내용을 발표자 노트로 옮겨라** —
    그래야 그림이 4.6in 을 다 쓴다(실측 6.1pt → 7.1pt).
- **검사**: `deck.diagram_svg()` 가 최소 pt 를 반환한다. 조립기가 전 도해의 중앙값·최솟값을 찍고
  6.5pt 미만을 경고한다.


### L-17 pptx 에 적는 글꼴 이름은 **상대 컴퓨터에 있는 것**으로, 폭은 **그 글꼴 기준**으로 잰다
- **원인**: SVG 에 쓴 `Noto Sans CJK KR` / `Noto Sans Mono CJK KR` 를 그대로 pptx 에 적으면
  맥·윈도에는 그 글꼴이 없어 PowerPoint 가 멋대로 대체한다. 그렇다고 이름만 `Consolas` 로 바꾸면
  이번엔 폭이 안 맞는다 — Consolas 의 advance 는 0.55em, Noto Sans Mono 는 0.50em 이라 **10% 넓어져**
  라벨이 상자를 삐져나온다.
- **규칙**: `svg2shapes.FONT_MAP` 으로 이름을 바꾸고(→ `맑은 고딕`·`Consolas`),
  `PROXY` 에 **(로컬 계측용 글꼴, 폭 비율)** 을 적어 둔다.
  폭이 넓어지는 글꼴이면 **상자를 넓히지 말고 글자 크기를 그 비율로 줄여** 설계한 폭을 지킨다.
  상자를 넓히면 그림 배치가 어긋난다.
- **검사**: `check_layout.py` 가 `rendered_width()`(같은 PROXY 표)로 재서 가로 넘침을 본다.
  생성기와 검사기가 **같은 표**를 봐야 한다.

### L-18 도해 안 글자를 슬라이드 글자와 중복시키지 마라
- **지적**: 감사에서 "SVG 첫 줄에 제목이 있는데 조립기가 같은 제목을 또 그린다 — 24장이 그렇다",
  "도해 아래 띠 문장이 콜아웃과 사실상 같다(유사도 0.97)" 가 나왔다.
- **원인**: 그림을 그리는 쪽과 슬라이드를 조립하는 쪽이 서로 뭘 쓰는지 모른 채 각자 제목·요약 문장을 넣었다.
  한 슬라이드에 24pt 제목 바로 밑에 15pt 로 같은 문구가 또 찍힌다. 30장 중 24장이 제목 중복이었다.
- **규칙**:
  1. **SVG 안에 슬라이드 제목을 넣지 마라.** `deck.diagram_svg()` 가 위에 제목과 밑줄을 그린다.
     패널 머리글(`① …`)도 SVG 가 아니라 `head=` 인자로 슬라이드 층에 그린다(L-31) —
     제목과 다른 문장이어야 한다는 규칙은 그대로다.
  2. **도해 안 문장을 `callout=` 이나 `items=` 에 옮겨 적지 마라.** 콜아웃에는 그림이 말하지 않은 것을 쓴다(L-07).
  3. 이미 제목이 든 SVG 를 고칠 때는 **그 `<text>` 한 줄만 지우면 된다.** `add_svg_shapes` 는 viewBox 가 아니라
     **내용 경계**(`content_bbox`)로 크기를 맞추므로 나머지 좌표를 옮길 필요가 없고, 오히려 그림이 커진다.
- **검사**: `check_layout.py` 의 `dup_texts()` — 그룹(도해) 안 글자를 (a) 슬라이드 제목
  (b) `핵심` 으로 시작하는 콜아웃과 정규화 후 비교해 유사도 **0.80 이상이면 실패**.
  실측 민감도: 제목을 그대로 둔 SVG = 100%, 콜아웃에 옮겨적기 = 97%, 정상 덱 = 0건.

### L-19 개요 슬라이드를 나중에 상세로 쪼갰으면, 개요를 반드시 다시 맞춰라
- **지적**: "슬라이드 20과 22가 틀린거래"
- **원인**: 선행연구 PiToMe 를 개요 한 장으로만 다루던 덱에 나중에 상세 세 장(에너지 점수·전후반 동작·보호 비교)을
  끼워 넣으면서, **앞선 개요 슬라이드를 그대로 뒀다.** 개요의 요약 표현이 새 상세와 정면으로 어긋났다 —
  "기준: 스펙트럼 에너지"(실제 기준은 이웃 유사도의 국소 에너지 `elu(cos−m).mean`),
  "공통: 이분 소프트 매칭"(뒤 절반 블록에서는 안 쓴다),
  "여기는 아무도 안 건드렸다"(블록마다 저에너지 토큰을 임시로 보호한다).
  요약은 상세가 없을 때는 "대충 맞는 말"이었는데, 상세가 붙는 순간 **틀린 말**이 됐다.
- **규칙**:
  1. 상세 슬라이드를 **추가하면, 같은 주제의 앞선 개요·요약 슬라이드와 비교표를 반드시 다시 읽고 고친다.**
     새 장만 만들고 끝내지 마라. 새 장이 앞 장을 반증하는지부터 본다.
  2. 개요의 **전칭 표현(공통·전부·모두·아무도·~뿐·항상·그대로)** 을 먼저 의심하라.
     상세가 붙는 순간 가장 먼저 거짓이 되는 표현이다.
  3. 남의 방법을 요약할 때 **논문 제목이나 홍보 문구를 기준의 이름으로 쓰지 마라**
     (PiToMe 의 기준은 "스펙트럼 에너지"가 아니다. 'Spectrum-Preserving' 은 증명한 성질의 이름이다).
     무엇을 근거로 적을지는 **L-20** 을 따른다 — 논문 본문이 1차 근거다.
- **검사**: `check_layout.py <파일.pptx> --absolutes` 가 **도해 라벨과 '핵심' 한 줄에 있는 전칭 표현만**
  슬라이드별로 뽑아 준다(본문 불릿까지 넣으면 잡음이 많아 아무도 안 읽는다 — 실측 81건 → 47건).
  자동 판정은 못 하므로 **추가·수정한 슬라이드 주변을 눈으로 확인**한다.

### L-20 남의 방법을 설명할 때는 **논문 본문이 1차 근거**다. 공개 구현은 논문과 다를 수 있다
- **지적**: "슬라이드 22의 앞과 뒤 절반으로 나누는 방식은 맞아? PiToMe.pdf에 논문 있으니 읽고
  pitome 관련 슬라이드 검증해줘"
- **원인**: 공개 구현 코드만 읽고 도해를 그렸다. 실제로 PiToMe 는 논문과 코드가 세 군데 달랐다 —
  (1) 논문에는 **블록을 앞뒤 절반으로 나눠 다른 알고리즘을 쓰는 규정이 없다**(코드에만 있다),
  (2) 마진이 논문 `m = 0.9 − 0.9·l_i/l` 인데 코드는 `0.75`,
  (3) 에너지 함수의 양의 구간이 논문 `f_m(x) = x` 인데 코드는 `elu(x − m)`.
  코드는 "실제로 돌아가는 것"이라 근거로 충분해 보이지만, **논문 발표에서는 논문이 곧 방법이다.**
  코드만 보고 그리면 발표 슬라이드가 통째로 틀린 말이 된다(도해 한 장을 두 번 다시 그렸다).
- **규칙**:
  1. 남의 방법을 슬라이드로 설명할 때 **원 논문 본문(수식·알고리즘 절)을 먼저 읽고 그것을 그린다.**
     PDF 가 없으면 arXiv 에서 받아 읽어라. **코드만 보고 그리지 마라.**
  2. 논문과 공개 구현이 다르면 **논문을 본문에 쓰고, 코드 차이는 각주 한 줄로 남긴다.**
     우리 실험이 코드를 썼다면 그 사실도 각주에 적는다 — 재현 수치의 근거가 달라지기 때문이다.
  3. 남의 방법을 다루는 도해에는 **근거 표기를 그림 안에 남긴다**(`논문 식 (4)`, `§3.2` 처럼).
     표기가 없으면 나중에 무엇을 보고 그렸는지 알 수 없어 같은 실수를 반복한다.
- **검사**: 눈으로 확인. 기계로는 못 잡는다 — 논문 PDF 와 코드를 대조하는 일이라 사람이 읽어야 한다.
  대신 규칙 3 의 근거 표기가 있으면 재검증이 몇 분으로 줄어든다.

### L-21 **우리** 실험을 옮길 때 "조건이 같다"류 정량 주장은 실험 코드로 재현해서 확인한다
- **지적**: "슬라이드 37과 38은 사실이야?"
- **원인**: 슬라이드에 `두 방법의 차이는 딱 네 개의 토큰이다` 라고 적었다. 우리 논문 본문·표 캡션의
  문장(`the two methods differ by exactly those four tokens`)을 그대로 옮긴 것이다.
  그런데 실험 코드의 병합 스케줄을 실제로 돌려 보니 달랐다 —
  `r = min(r, (T − n_protect)//2)` 캡 때문에 **12블록이 보는 토큰 수는 261→41 로 두 방법이 완전히 같고
  (백본 FLOP 동일)**, 갈라지는 것은 마지막 블록 **뒤**의 병합뿐이라 21개 vs 23개, 즉 **2개**다.
  L-20 은 "남의 방법은 논문이 1차 근거"였는데, **우리 결과는 반대다 — 코드가 1차 근거고 논문 문장이 파생물**이다.
  파생물을 베끼면 논문의 부정확이 슬라이드로 그대로 전파된다(게다가 사실보다 불리하게 적혀 있었다).
- **규칙**:
  1. 슬라이드에 **"같은 예산 · 동일 조건 · N개 더 남긴다 · 개수만 다르다"** 같은 *정량 조건* 주장을 쓸 때는,
     논문 문장을 옮기지 말고 **실험 코드의 스케줄을 실제로 돌려 숫자를 뽑아 확인한다.**
     정확도 값 같은 *측정치*는 옮겨도 되지만, **조건 주장은 코드에서 재도출한다.**
  2. 재현 결과가 논문과 다르면 **논문 쪽이 틀린 것일 수 있다.** 슬라이드는 코드 기준으로 적고,
     논문의 해당 문장을 사용자에게 보고한다(우리 논문도 감사 대상이다).
  3. 조건이 정말 같다는 것을 확인했으면 **왜 같은지 한 줄로 근거를 남겨라**
     (`12블록 모두 같은 개수씩 병합 · 백본 FLOP 동일`). 그래야 질문이 나왔을 때 방어된다.
- **검사**: 눈으로 확인 + 재현 스크립트. 조건 주장이 있는 슬라이드는 그 근거를 낸 코드 한 줄을
  발표자료 소스(`발표자료_src/`)의 설계서에 함께 적어 둔다.

### L-24 도해 안의 상자에 문장을 채우면 그림이 아니다 — 구조가 모양으로 보여야 한다

### L-25 도해는 예약 박스의 위에 붙이고, 설명은 실제 그림 높이 바로 아래에 — 빈 띠를 만들지 마라

  실제 그림 높이(gh)가 아니라 **예약 높이(dh) 아래**에 붙였다. 가로로 넓적한 도해(폭 맞춤 후 세로가 남는
  것)는 위·아래에 빈 띠가 생겼다 — 실측 conv 덱: 도해↔설명 간격 1.33~1.61in, 한 장은 위쪽에 0.9in 공백.

  세로가 긴 도해가 눌린다(L-30 축척 검사에 걸림) — 그때는 SVG 세로를 압축한다.
- **검사**: `check_layout.py` 의 `diagram_gap()` — 도해↔설명 간격이 0.18~0.45in 밖이면 실패,
  머리글↔도해 간격이 0.18in 미만이어도 실패. 어긴 입력 두 방향 모두 검출 확인
  (넓음: v2 초판 4장 1.3~1.6in / 좁음: v2.3 8건 0.12~0.14in), 고친 뒤 0건.

### L-27 도해 안 라벨과 화살표·테두리가 닿지 않게 — 자동 검사가 못 잡는 겹침이 있다
- **지적**: "'회색 = 제로 패딩'이란 문구가 큰 둥근 사각형의 라인에 걸치고, '가중치'라는 말도 점선 화살표와 겹쳐."
- **원인**: `check_layout` 의 겹침 검사는 **글자 있는 도형끼리**만 본다. 글자 vs 선·테두리·화살표는 검사 밖이라
  통과했다. 차선 상자의 경계선 위에 캡션을 얹고, 점선 화살표 옆에 라벨을 세로로 나란히 붙인 것이 원인.
- **규칙**: 캡션은 **그 캡션이 설명하는 도형의 바로 아래(또는 위)** 에 붙이고, 그 자리가 다른 상자의 경계선과
  겹치면 **상자를 키워 안에 넣거나** 캡션을 상자 밖 여백으로 옮긴다. 화살표 라벨은 화살표에서 최소 글자 높이만큼
  띄운다. 캡션을 옮길 때는 **옮긴 자리를 렌더해서 다시 본다** — 이번에 한 번 옮긴 자리가 또 다른 선에 걸렸다.

### L-28 마지막에 "요약·정리" 슬라이드를 붙이지 마라

### L-29 "실증 ✓" · "@" 같은 기계 투를 도해에 쓰지 마라. 설명은 상자가 아니라 글머리 기호로
- **지적**: "'실증 ✓', '1024×16 @ 16×16'와 같은 AI스러운 반응들은 빼줘." · "그림 아래에 박스를 여러 개 그리고

  상자를 작게 줄였을 뿐 "상자 나열" 자체는 남긴 것.
- **규칙**: 도해 안 라벨은 **사람이 발표에서 말하듯** 쓴다 — "검증됨: softmax", "패치 1024×16 · W 16×16".
  ✓·@·→(문장 안)·이모지 금지. 그림 아래 설명은 반드시 `diagram_svg(items=[...], cols=1)` 의 **글머리 기호**로
  넣고, 도해 SVG 안에 설명용 상자 행을 그리지 않는다. 도해 안 글자는 라벨과 머리글·결론 각 1줄까지.
- **검사**: 눈으로 확인 + `text_heavy()`(L-24) 가 상자 나열을 경고한다.

### L-30 덱 전체에서 글자 크기는 역할별로 고정한다 — 글머리 12pt, 도해는 같은 축척
- **지적**: "슬라이드 별로 글머리 기호를 사용한 문장의 글씨 크기와 그림 속 설명의 글씨 크기가 제각각이야.
  글씨 크기 통일시켜주고, 글머리 기호 문장은 12로 맞춰줘. 지금 11인 문장은 너무 작더라."
- **원인**: 두 겹이다. ① `_fit()` 이 슬라이드마다 "들어가는 최대 크기"를 골라 글머리가 11/14/19pt 로
  널뛰었다(내용량이 적은 장일수록 커짐 — 실측). ② 도해는 내용 bbox 로 폭 맞춤하는데 SVG 마다 내용
  폭이 달라(575~918) 축척이 0.95~1.51 배로 달라졌고, 같은 명목 9.5pt 가 장마다 다른 크기로 렌더됐다.
- **규칙**:
  1. 도해 슬라이드의 글머리는 `deck.DIA_ITEM_PT = 12` 고정. 안 들어가면 크기를 줄이지 말고 **문장을 줄인다**.
  2. SVG 글자는 4단 팔레트로만: 머리글 13 · 굵은 라벨 11.5 · 본문 11 · 캡션 10.5 (기호 16 예외).
     (사용자가 "그림 안 글씨 전체적으로 조금씩 키워줘" 로 +1pt 상향, 2026-08-14 — 렌더 최소 ≥10pt)
  3. 한 덱의 SVG 들은 **내용 폭을 ~918 로 통일**한다(여백 분배로 채움). 폭이 다르면 축척이 달라진다.
     세로가 눌리지 않게 viewBox 높이는 설명 줄 수를 감안해 (3줄 기준) ≤ 330 으로.
- **검사**: `check_layout.py` 의 `bullet_and_scale()` — 도해 아래 글머리 run 이 12pt 가 아니면 실패
  (꼬리말 제외), 도해 그룹 폭이 최대폭의 97% 미만이면 축척 불일치로 실패.
  어긴 입력(v2.1, 11/14/19pt)으로 13건 검출, 고친 덱 0건·폭 균일도 99.3% 확인.

### L-31 도해 머리글은 SVG 밖 슬라이드 층에 14pt 검정 고정 — 번호는 슬라이드 순서대로
- **지적**: "'① 창이 훑은…' 같은 소제목이 왜 슬라이드마다 글씨 크기가 달라? 통일시켜달라고 했잖아.
  최소 14로 해줘. 글자색도 검은색으로. 그리고 번호가 왜 ①로 고정되어 있어? 유도리있게 번호도 매겨."
- **원인**: 머리글을 SVG 안에 넣으니 도해 축척(내용 폭 편차)을 그대로 타서 12.2/11.9pt 로 갈라졌다.
  L-30 으로 폭을 99.3% 까지 맞춰도 소수점 차이가 남는다 — SVG 안 글자는 근본적으로 크기를 고정 못 한다.
  번호는 L-18 예시의 "①" 을 기계적으로 복붙해 모든 장이 ① 이었다.
- **규칙**:
  1. 머리글은 SVG 에 넣지 않는다. `deck.diagram_svg(head="② …")` 로 넘기면 슬라이드 층에
     `DIA_HEAD_PT = 14`, 굵게, INK(검정) 로 그린다 — 축척과 무관하게 전 장 동일 크기.
  2. 번호는 표지 다음 도해부터 ①②③… 슬라이드 순서대로 매긴다. 같은 번호를 두 장에 쓰지 않는다.
  3. SVG 첫 줄 규칙(L-18 의 "① 소제목")은 이것으로 대체된다 — SVG 는 순수 그림 + 라벨만.
- **검사**: `check_layout.py` 의 `head_check()` — ① 그룹 안에 원문자로 시작하는 글자가 있으면
  "머리글이 SVG 안에 있음" 실패, ② 슬라이드 층 머리글이 14pt 아니면 실패, ③ 번호가 장끼리 중복이면 실패.
  어긴 입력(v2.2, SVG 안 ①×4)으로 4건 검출, 고친 덱 0건 확인.

### L-32 팔레트는 3계열 — 무채(잉크·회색) + 강조 1색 + 하이라이트 1색. 색 글자 금지
- **지적**: "그림 설명도 검은색으로 해주고, 그림 만들 때 색의 다양성을 덜 주었으면 좋겠어.
  지금은 너무 알록달록해. 불필요한 부분에 색 넣는 걸 자제해줘."
- **원인**: L-13 의 "색으로 의미 구분(파랑·주황·초록·빨강)"을 기계적으로 적용해 한 덱에
  강조 색상군이 5개(파랑·초록·주황·빨강·노랑)까지 쌓였다. 캡션·결론 문장까지 초록/주황 글자였다.
- **규칙**:
  1. 한 덱의 팔레트는 3계열로 제한한다: **무채**(잉크 #16202c·회색들·흰색) 기본,
     **강조 1색**, **하이라이트 1색**(추적 원소, 예: 노랑 #ffd34d).
     강조색의 기본값은 **#253761 계열(짙은 남색)** — 사용자가 "일반적인 파란색 말고 253761 계열"
     을 지정했다(2026-08-14). 채움은 틴트로 유도한다: 연한 채움 = tint 0.87, 중간 = tint 0.55
     (`tint(c,f) = c + (255-c)·f`). 저채도 남색이라 연한 틴트는 회색에 가깝다 — 강조는 진한
     스트로크(#253761)와 굵기가 담당한다.
  2. **글자는 잉크(검정) 아니면 회색이다.** 색 글자는 쓰지 않는다 — 강조는 굵기로.
  3. 의미 구분이 더 필요하면 색이 아니라 **선 스타일(실선/점선)·굵기·채움 농도**로 한다.
     (예: 순서도의 예/아니오 = 실선/점선 + 라벨, 창 2개 = 파랑 실선/회색 점선)
  4. L-13 의 4색 규칙은 이 규칙으로 대체된다.
- **검사**: `check_layout.py` 의 `accent_hues()` — 도형 채움·선 색에서 무채색을 뺀 색상군(hue 6분할)이
  3군 이상이면 실패. 어긴 입력(v2.4, 파랑·초록·빨강 3군)으로 1건 검출, 고친 덱(파랑·노랑 2군) 0건.

### L-33 글자를 키우면 상자와 그림도 함께 키운다 — 렌더 최소 11pt, 라벨은 상자 안에
- **지적**: "'패치 1024×16 · W 16×16' 같이 박스를 넘어가는 글자들 없게 해줘. 설마 진짜로 글씨 크기만
  키우고 그거에 맞게 그림 크기는 안 키운 거야? 너 센스없다.. 그림 속 글자 크기 최소 11로 해주고
  그에 맞게 그림 크기도 조정해줘."
- **원인**: 글자 크기 요청을 **명목 크기 +1pt 치환**으로만 처리하고, 그 글자가 들어앉는 상자 폭과
  도해 전체 배율은 그대로 뒀다. 라벨이 상자를 삐져나왔는데 기존 가로 넘침 검사는 못 잡았다 —
  svg2shapes 가 라벨마다 독립 텍스트박스를 만들어 "라벨 vs 뒤에 깔린 상자" 관계를 모르기 때문.
- **규칙**:
  1. 글자 크기 변경은 **삼위일체**다: 명목 크기 + 그 글자를 담는 상자 치수 + 도해 내용 폭(=렌더 배율)을
     같이 조정한다. 렌더 크기 목표(현재 최소 11pt)에서 역산해 내용 폭을 정한다:
     `내용 폭 = 본문 폭(870pt) × 명목 최소 / 렌더 최소` (예: 10.5/11 → 828).
  2. 상자가 좁으면 글자를 줄이지 말고 **상자를 넓힌다**(사용자가 명시한 방향).
  3. 내용 폭을 바꾸면 세로가 긴 도해가 눌린다 — L-30 축척 검사에 걸리면 그 도해의 세로를 압축한다.
  4. 큰 컨테이너(차선·패널)의 경계에 걸친 라벨은 자동 검사 밖이다 — 렌더를 눈으로 본다(L-27).
  5. **추가 지적(2026-08-14)**: "'b 16개'가 너무 박스와 딱 맞아. 여유 공간이 조금은 있어야 자연스럽지" —
     라벨은 상자 안에 **좌우 여유**를 두고 앉힌다. 넘지만 않으면 되는 게 아니다.
     상자 폭 ≥ 추정 글폭 + 양쪽 0.08in(글폭 추정이 낙관적이라 넉넉히). 격자 칸의 한두 글자는 예외.
  6. 도해 안 결론 문장이 설명 글머리와 같은 말이면 **문장을 옮기지 말고 지운다** — 이번 겹침
     ("층 하나 = 왕복 1회…")의 원인이 중복 문장을 도해 바닥에 우겨넣은 것이었다(L-24 연장).
- **검사**: `check_layout.py` 의 `label_fit()` — 그룹 안 라벨의 중심을 포함하는 가장 작은 라벨급
  상자(높이<0.9in, 폭<3.2in)를 찾아 ① 라벨이 0.03in 이상 삐져나오면 "넘침" ② 좌우 여유가
  0.08in 미만이면 "꽉참"으로 실패(길이<3자 or 상자 폭<0.3in 인 격자 칸은 제외).
  어긴 입력으로 넘침 2건(v2.6)·꽉참 2건(v2.7, 사용자 지목 'b 16개' 포함) 검출, 고친 덱 0건.

### L-06 "그릴 수 있겠다 싶으면 그린다"
- **지적**: "글 말고 그림으로 그려서 표현할 수 있는 슬라이드들이 굉장히 많이 보이는데 … 그림으로 그려줘"
- **규칙**: 다음 신호가 보이면 글이 아니라 그림으로 만든다 —
  포함 관계, 데이터 흐름, 분할·배치, 좌우 비교, 루프 중첩, 시간 겹침, 수치 비교, 표기법 해설.
  단순 나열·인용문·이미 표로 충분한 것은 그리지 않는다.
- **검사**: 눈으로 확인.

### L-07 그림 옆 설명은 "그림이 말하지 못하는 것"만 남긴다
- **지적**: "기존 설명은 그림을 이해하는데 필요한 중요한 내용은 생략되지 않게 요약해줘"
- **규칙**: 원래 불릿을 3~6개로 줄이되, **그림에 이미 그려진 것을 글로 반복하지 마라.**
  남길 것은 근거(출처 문장), 수치의 출처, 주의사항, 함의다. 수치는 절대 지어내지 않는다.
- **검사**: 눈으로 확인.

### L-08 글자가 상자를 넘지 않게 계산하고 그린다
- **원인**: 한글은 글자 폭이 영문의 2배인데 이를 무시하고 상자를 잡으면 반드시 넘친다.
- **규칙**: 한글 1자 ≈ font-size × 1.0, 영문·숫자·공백 1자 ≈ font-size × 0.5.
  상자 폭보다 **최소 12pt 여유**. 줄 간격은 font-size × 1.35.
- **검사**: `check_layout.py` 의 가로/세로 넘침 검사. 0 이어야 한다.

## G. 스킬 사용 방식

### L-14 변환은 `HTML → PPTX` 와 `PDF → PPTX` 두 갈래다
- **지적**: "아니아니 html -> pdf -> pptx가 아니라 html -> pptx or pdf -> pptx야"
- **원인**: WeasyPrint 가 PDF 만 낸다는 구현 사정을 그대로 사용법에 노출해,
  HTML 을 PPT 로 만들려면 PDF 를 먼저 만들어야 하는 것처럼 문서를 썼다.
  사용자에게는 단계가 하나 늘어난 것으로 보인다.
- **규칙**: 사용자에게 보이는 변환은 두 개뿐이다 — `html2pptx.py`, `pdf2pptx.py`.
  HTML→PPTX 는 **중간 PDF 파일을 만들지 않는다**(WeasyPrint 바이트를 메모리에서 받는다).
  PDF 도 필요하다고 명시할 때만 `--keep-pdf` 로 함께 낸다.
  구현 사정을 사용법으로 새어 나가게 하지 마라.
- **검사**: 변환 전후로 작업 디렉터리의 `*.pdf` 개수가 같아야 한다(`--keep-pdf` 없을 때).
